# Воркфлоу: выкатка на продакшн

Порядок один для всех проектов. Конкретика — ветка выкатки, имя workflow, что
делает сервер, что проверять после — лежит в разделе «Выкатка» файла
`docs/projects/<активный>/project.md`. Активный проект — в
`docs/projects/.active`.

Здесь конкретики нет намеренно: два описания одного и того же неминуемо
разойдутся, и выкатка пойдёт по устаревшему.

## Шаг 0 — Чья выкатка

Прочитай `.active` и раздел «Выкатка» проектного файла. Раздела нет — это
находка: спроси, а не придумывай порядок сам. Каталоги кода проекта — в
`docs/projects/README.md`, колонка «Код в репозитории».

## Шаг 1 — Предвыкаточная проверка

Запусти параллельно:
- `performance-optimizer` — нет критичных проблем скорости
- `silent-failure-hunter` — нет тихих ошибок
- `security-secrets-scanner` — нет утечек секретов
- `rkn-compliance` — правовая обвязка (согласия, политика, cookie, реквизиты)

Находка уровня БЛОКЕР у `rkn-compliance` останавливает выкатку: сайт,
собирающий персональные данные без корректного согласия, в прод не уходит.

Есть новые миграции — добавь `migration-guard`. Деструктивная миграция без
свежего бэкапа — блокер.

## Шаг 2 — Ветка готова

Всё закоммичено и запушено в рабочую ветку. Сборка проходит во всех каталогах
кода проекта, типы чистые, тесты зелёные. Красную ветку не выкатывать.

## Шаг 3 — Выкатка

Пуш рабочей ветки в ветку выкатки проекта. Сервер сливает `--ff-only`, поэтому
ветка выкатки всегда предок рабочей — своих коммитов в ней не бывает.

```bash
git push origin <рабочая ветка>:<ветка выкатки>
```

Дальше работает GitHub Actions: бэкап, сборка, миграции, перезапуск, health.
Руками по SSH на сервер не ходим — иначе состояние сервера разойдётся с
репозиторием, и следующий прогон это обнаружит слиянием.

## Шаг 4 — Следить за прогоном

`mcp__github__actions_list` (`list_workflow_runs` по ветке выкатки), логи
упавшего шага — `mcp__github__get_job_logs`.

**Выкатка не закончена, пока последний прогон не `success`.** Запушил и ушёл —
не выкатил.

## Шаг 5 — Проверка после

Ключевой пользовательский сценарий проекта от начала до конца — какой именно,
сказано в его `project.md`. Плюс всегда: сайт открывается по HTTPS, процесс
поднялся, логи без критичных ошибок.

## Шаг 6 — Откат

Откат — это тоже выкатка: новый коммит с `git revert` уходит тем же путём,
через ветку выкатки. Правку прямо на сервере не делаем никогда — она
потеряется при следующем прогоне и оставит расхождение, которое потом ищут
часами.

Если сломалась миграция — порядок отката описывает `migration-guard` в своём
отчёте, до выкатки, а не после.
