# Обязательный цикл до соответствия ТЗ

Этот контракт действует для feature, bugfix, review, UI, безопасности и инфраструктуры.
Наличие файлов агентов или зелёная проверка синтаксиса не заменяют результат задачи.

## Степень задачи и ответственность

- routine: небольшая обратимая правка. Координатор фиксирует критерии и проверку;
  независимый code-reviewer подтверждает результат. Не запускать все отделы.
- standard: функциональная задача. researcher/planner по необходимости, coder,
  профильные ревьюеры, общий fallback и проверка секретов.
- critical: деньги, доступы, риск-движок, миграции, инцидент, публикация.
  Дополнительно qa-engineer, silent-failure-hunter и предметные security/DB роли.

Координаторы: основной агент, orchestrator, design-department,
security-department, seo-department. Конечный специалист выполняет выданную
область сам и не делегирует её заново по общему правилу. Самопроверка
исполнителя полезна, но не считается независимым ревью.

## Исполнение

1. Зафиксировать конкретное ТЗ и проверяемые критерии; выбрать степень задачи.
2. Инициализировать task_gate.py с criterion, required-check и настоящей
   идентичностью implementer. Использовать ID текущей сессии из SessionStart. Для параллельной работы
   задать --scope с точными файлами/каталогами; без него scope — весь репозиторий.
3. До реализации получить scope через `python3 .codex/scripts/changes.py`.
   Инструмент включает staged, unstaged, untracked и удаления. Для уже
   закоммиченной работы передавать --base с SHA начала задачи.
4. Выполнить реализацию, затем необходимые тесты. Записать фактические
   результаты, не считать skip или отсутствие среды успешным тестом.
5. Передать ревьюерам ТЗ, критерии, scope, текущую revision, результаты тестов
   и фактические ограничения. Общий code-reviewer покрывает Python, shell,
   YAML и прочие области, для которых нет отдельной роли.
6. Независимые ревью запускать волнами в пределах свободных слотов.
   Учитывать уже работающих координаторов. Ждать завершения волны и
   освобождать завершённые потоки до следующей. Не повышать лимит вслепую.
7. Каждой подтверждённой находке назначить владельца. Она остаётся открытой,
   пока исправление не проверено. Дедупликация не означает молчание:
   если профильный владелец не запущен, сообщить находку координатору.
8. Исправить дефекты. Любое изменение revision делает предыдущие pass
   устаревшими: повторить затронутые тесты, связанные сценарии и независимое
   ревью текущей revision. Не закрывать находки одной записью «исправлено».
9. Продолжать шаги 4–8, пока все критерии ТЗ и обязательные проверки не
   подтверждены и нет незакрытых подтверждённых дефектов.
10. Сохранить смысловой итог в .codex/context.md или .codex/sessions/,
    проверить итоговый scope, затем закрыть task_gate.py complete.
11. Только после успешной проверки готовности — коммит/пуш и разрешённая
    публикация по runbook. После публикации — её проверка.

## Работа с task gate

Все доказательства привязаны к revision (HEAD + baseline + содержимое файлов).
Не подставлять выдуманную личность ревьюера или факт выполнения команды.
Gate проверяет полноту и актуальность записей, а не истинность произвольного текста.

```bash
python3 .codex/scripts/task_gate.py init --task TASK_ID --level standard \
  --owner-session SESSION_ID --implementer IMPLEMENTER_ID \
  --criterion acceptance --required-check regression
python3 .codex/scripts/task_gate.py status --task TASK_ID
python3 .codex/scripts/task_gate.py criterion --task TASK_ID --name acceptance --evidence 'проверенный сценарий'
python3 .codex/scripts/task_gate.py check --task TASK_ID --name regression --status pass --evidence 'команда и её результат'
python3 .codex/scripts/task_gate.py review --task TASK_ID --name code-reviewer \
  --reviewer REVIEWER_ID --status pass --evidence 'отчёт независимого ревью текущей revision'
# Записать остальные роли, перечисленные status, с их реальными отчётами.
python3 .codex/scripts/task_gate.py complete --task TASK_ID
```

Stop-хук возвращает активную задачу на доработку, пока gate не готов.
Отсутствие прогресса — не повод бесконечно повторять неизменённый вызов.
При недоступном сервисе, противоречивом ТЗ или решении Гермеса записать
`blocked --evidence 'конкретная причина'` и сообщить блокер. Это не готовность.
Не выполнять новые платные/необратимые действия ради получения pass.

## Формат результата ревью

Роль и reviewer ID; scope/revision; проверенные критерии; findings
(ID, важность, путь, воспроизведение); выполненные проверки; ограничения;
verdict pass/fail. Чистое ревью допустимо. Недостаток данных — блокер,
а не выдуманная находка и не безусловный pass.
