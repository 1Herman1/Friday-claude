## 0. Коротко

Код находит сетап и считает риск. LLM только оценивает сигнал (ВЗЯТЬ/ПРОПУСТИТЬ) и разбирает сделки. Исполняет код со стопами на стороне биржи. Всё пишется в общую PostgreSQL, дневник показывает сделки агентов. Путь: сигналы (есть) → бумажная торговля → демо-счёт по API → арена моделей → проп, где автоматизация разрешена.

Движок пишем **сами** поверх проверенных библиотек (ccxt, SDK площадок, pandas, pydantic). Готовые фреймворки (freqtrade, Nautilus, TradingAgents) **не берём ядром**, а используем как образец и для сверки. Почему — §9.1.

## 1. Цель и границы

**Цель.** ИИ-агенты, сгруппированные в кластеры по стратегиям, торгуют сначала на демо, затем на крипто-пропах, где автоматизация разрешена. Система сама ищет улучшения, но не может ослабить риск-лимиты.

**Входит:**
- данные рынка, детекторы сетапов, LLM-оценка сигнала, риск-слой, исполнение, сторож;
- бумажная торговля, бэктест, форвард-тест, арена {модель × кластер × площадка};
- журнал всех решений в общую БД, отчёты и управление через Telegram (Hermes);
- улучшатели: разбор сделок, новая версия стратегии в тени.

**Не входит:**
- шорт пампов (бот сигналов — Т4, на пропы не идёт);
- арбитраж (Т7);
- веб-интерфейс: сделки агентов показывает дневник (Т6);
- торговля на площадках, где автоматизация запрещена, и любая маскировка бота под человека.

## 1b. Решения Германа (12.10, ответы на вопросы в Т1)

- **Цель продукта:** автономная система торговли ИИ-агентов на пропах. Сигналы и SaaS — потом, вторым шагом.
- **Деньги:** на старте $0 на челленджи. Сначала агенты 2–3 месяца работают на демо. Когда покажут хоть какой-то плюс — маленькие челленджи ($5–10k счёт).
- **Стратегии:** тестируем много разнородных (от скальпинга до сделок раз в месяц), отбираем 3–4 рабочие и работаем с ними на дистанции. Каталог стратегий — исследование `research/strategies-catalog.md`.
- **Агенты:** агент = стратегия × площадка; агентов столько, сколько площадок у каждой стратегии. На старте работают изолированно, координирует только риск-слой.
- **Роль LLM:** решение «входить или нет» на пересечении факторов: сигнал, контекст графика, риск, сентимент.
- **Площадки:** пропы + свои счета на Hyperliquid и MEXC (несколько вариантов параллельно).
- **Сервер 24/7:** да.
- **Автономия:** сразу полная автономия (без подтверждения кнопкой). Цель — доходность именно автономной системы, а не быстрый результат. Kill-switch и лимиты риска остаются.
- **Открыто:** доступ к площадкам из страны Германа и способ оплаты (ответит позже).

**Метрика отбора стратегии — матожидание в R после комиссий на достаточном числе сделок, а не winrate.** Winrate 50% при RR 1:2 = +0,5R на сделку до комиссий; при RR 1:1 тот же winrate — минус на комиссиях. На 5m со стопом 0,1% комиссия taker туда-обратно (~0,1%) съедает до 1R. Демо оцениваем по числу сделок (≥100 на стратегию), а не по календарю.

## 1a. Это мультиагентная система

Система — набор независимых агентов, а не один бот.
- **Торговый агент = кластер + версия стратегии + модель + площадка + свой счёт.** Например «smc-btc v0.2 × Opus × Propr Beta». Агентов много, они работают параллельно и сравниваются на арене.
- **Кластер** — группа агентов одной стратегии (SMC-BTC, MA-cross, News & Sentiment). У кластера общий детектор и карточка, у агентов разные модели, площадки и версии.
- **Роли внутри агента** (мозг, §6.3): аналитик контекста, «глаза» по графику, новости, Bull и Bear, трейдер-решатель. В минимальном варианте одна роль, полный включаем, если он выиграет на арене.
- **Служебные агенты, общие для всех:** риск (код), исполнение (код), Сторож (код), улучшатели (LLM: разбор сделок, исследователь стратегии, тени), диспетчер (Hermes).
- **Общая память агентов** — репозиторий (карточки, промпты, версии) и БД (сигналы, решения, сделки). Чат — только вход.
- Агенты не могут менять лимиты риска и друг друга; новую версию агента включает только Герман после победы в тени.

## 2. Принципы (не меняются без решения Германа)

1. **Код ищет и считает, LLM оценивает, риск решает код.** Уровни входа, стопа, тейка и размер считает только код. В тесте 07.10 модели на одних свечах дали разные уровни, часть — с отрицательным R:R.
2. **LLM вызывается только при сигнале детектора.** Нет сигнала — нет вызова.
3. **Риск-лимиты меняет только Герман.** Агентам и улучшателям файлы лимитов доступны только на чтение. API для изменения нет.
4. **Невалидный ответ LLM = HOLD.** Любая ошибка = не торговать.
5. **Стоп выставляется на бирже вместе с входом.** Позиция без стопа на бирже — аварийная ситуация, Сторож закрывает её.
6. **Агент видит только прошлое:** данные хранятся с временем публикации, работаем только по закрытым свечам.
7. **Без маскировки.** Автоматизация только там, где она разрешена правилами площадки или письменным разрешением.
8. **Контекст живёт в репозитории, а не в чате.** Правка стратегии = новая версия карточки, тень, замена.
9. **Числа — Decimal(38,18)**, float для денег запрещён (решение 11.10).
10. **Сначала бумага и демо.** Реальные деньги — только после критериев §12 и подтверждения Германа.

## 5. Как проходит один сигнал

```
свеча закрылась → Данные → Детектор ──нет сетапа──▶ стоп (LLM не вызывается)
                               │ signal.v1
                               ▼
                         Мозг (LLM) ──невалидно/ошибка──▶ HOLD
                               │ decision.v1 (ВЗЯТЬ/ПРОПУСТИТЬ, уровни не меняет)
                               ▼
                         Риск-слой ──REJECT──▶ журнал + Telegram
                               │ APPROVE/REDUCE + qty
                               ▼
                         Исполнение: лимитный вход + стоп + тейк на бирже
                               ▼
                         Order Manager ведёт позицию → fills → журнал → дневник
                               ▼
                         Улучшатели (по расписанию): разбор, предложения
```

Каждый шаг пишет запись в БД с общим `signal_id`. Цепочку «сигнал → решение → риск → ордер → исполнение → результат» можно восстановить по любой сделке (`/why <id>`).

## 6. Требования к модулям

Папки — по `shared/DATA_ARCHITECTURE.md` §6: общий пакет `shared/python/tp_core` (БД, коннекторы, деньги, LLM-шлюз) и движок `prop-agents/engine` (`tp_engine`).

### 6.1 Данные (`engine/data/`, код)
- Свечи OHLCV: MEXC (основной источник сейчас), площадка исполнения (Hyperliquid, OKX, BloFin). Через ccxt; WebSocket — с P4.
- Только закрытые свечи. Время в UTC, хранится время открытия и закрытия свечи.
- MEXC: не больше 500 свечей за запрос, листаем с ретраями и паузой (уже решено в детекторе).
- Деривативы: фандинг, открытый интерес, ликвидации — раз в 1–5 мин (с P4).
- Новости и календарь (FOMC, CPI, разлоки) — источники выбрать (открытый вопрос); у каждой записи время публикации.
- Кэш свечей в БД или parquet; повторный прогон истории не ходит в сеть.
- Проверка качества: пропуски свечей, дубли, скачки времени → в лог и в `risk_events`, детектор по дырявым данным не работает.

### 6.2 Детекторы (`clusters/<имя>/`, `engine/detectors/base.py`, код)
- Общий интерфейс: `run(candles, config) → list[signal.v1]`. Один детектор на кластер.
- Жёсткие числа — в `config.json` / `rules.yaml` кластера; меняет только Герман.
- Ключ сигнала: символ + ТФ + кластер + версия + время сетапа + сторона. Повторный прогон даёт те же ключи (идемпотентность).
- Время вместо номеров свечей: `sweep_time`, `choch_time`, `fvg_time`, `fill_time`, `exit_time`.
- Статусы: `pending → open → win / loss / expired / cancelled`; live-прогон обновляет открытые.
- В истории считаются R и R после комиссий и проскальзывания (модель комиссий — по площадке).
- Картинка сетапа с разметкой → PNG (для Т5 и для Chart Vision).
- Сверка: на той же истории прогоняем библиотеку `smart-money-concepts` (§9.2) и сравниваем свинги, FVG, BOS/CHoCH. Расхождения разбираем с Германом. В бою работает наш детектор.
- Кластеры: SMC-BTC (есть), MA-cross (бейзлайн, P4), News & Sentiment (после выбора источников).

### 6.3 Мозг кластера (`engine/brain/`, LLM)
- Запускается только при новом сигнале.
- Минимальный вариант (P2): одна роль Strategy Trader — получает сигнал, картинку, контекст рынка, карточку стратегии → `decision.v1` (ВЗЯТЬ/ПРОПУСТИТЬ + причины). Уровни не меняет.
- Полный вариант (P4+): Context → Chart Vision → News → Bull/Bear → Strategy Trader (как в `ARCHITECTURE.md`). Включаем, только если арена покажет, что он лучше минимального.
- Ответ проверяется по JSON Schema (pydantic). Невалидный ответ, таймаут или ошибка → HOLD.
- Каждый вызов пишется в `llm_calls`: модель, промпт (хэш + текст), ответ, токены, стоимость, задержка.
- Промпты версионируются в репо (`engine/brain/prompts/<роль>.v<N>.md`).
- Бейзлайн без LLM работает параллельно всегда: тот же детектор берёт все сигналы. Так видно, добавляет ли LLM пользу.

### 6.4 Риск-слой (`engine/risk.py` → `engine/risk/`, код) — есть
- Уже сделано: см. `engine/README.md`.
- Доработать: читать профили и лимиты из БД после P3 (только чтение, изменения — новой записью с историей); писать каждое решение в `risk_evaluations`; учитывать комиссию и проскальзывание в риске сделки; проверка спецификации инструмента с площадки (шаг лота, мин. объём, тик).
- Тесты: каждое правило — отдельный тест; мутационные тесты только в копии worktree.

### 6.5 Исполнение (`tp_core/connectors/`, `engine/execution/`, код)
- Единый интерфейс адаптера: `get_balance`, `get_positions`, `get_open_orders`, `place_order` (вход + стоп + тейк), `cancel`, `get_fills`, `get_instrument_spec`.
- Адаптеры по порядку: **paper** (свой симулятор по живым свечам, P2) → **Hyperliquid testnet** и/или **OKX Demo** (P4) → **BloFin demo** (для HyroTrader) → **Propr Beta → Propr** (P5).
- Вход лимиткой (задержка оркестрации 1–5 мин); если цена ушла за вход больше чем на X% — отмена.
- Идемпотентность: `client_order_id` от `signal_id`; повторная отправка не дублирует ордер.
- Стоп и тейк на стороне биржи сразу после входа (или вместе с ним, если площадка позволяет).
- Ключи API — только в `.env`, права: торговля без вывода средств. Для Hyperliquid — отдельный API-кошелёк (agent wallet), не основной ключ.
- Терминал в браузере (SizeProp) — только где автоматизация фронтенда разрешена, отдельным этапом после API.

### 6.6 Order Manager (`engine/execution/`, код)
- Ведёт позицию: частичные тейки, безубыток, трейлинг, выход по времени — по правилам карточки.
- Сверяет состояние с биржей каждую минуту; источник правды — биржа.
- Пишет ордера и исполнения в БД (`executions` — единица правды, сделка собирается из fills).

### 6.7 Журнал (`tp_core/repo/`, код)
- Пишет: сигналы, решения LLM, вызовы LLM, решения риска, ордера, исполнения, фандинг, комиссии, события сторожа.
- До P3 — файлы JSONL в `clusters/<имя>/out/` (в .gitignore); после P3 — PostgreSQL, `seen.json` заменяется уникальным ключом.
- Дневник (Т6) показывает сделки агентов с `executor = AGENT` и ссылкой на `signal_id`.

### 6.8 Бэктест и форвард-тест (`engine/backtest/`, код)
- Свой событийный прогон по закрытым свечам тем же кодом детектора и риска, что в бою (не отдельная «бэктестовая» версия).
- Комиссии и проскальзывание по площадке; фандинг для перпетуалов.
- Метрики: число сделок, winrate, средний R, PF, макс. просадка, R после комиссий, серия убытков — через `quantstats` + свои R-метрики.
- Защита от подгонки: walk-forward (подбор на одном отрезке, проверка на следующем); все прогоны пишутся с версией конфигурации.
- vectorbt — только для быстрых переборов параметров при исследовании, не для решений (§9.2).

### 6.9 Арена (`engine/arena/`, код)
- Ячейка = кластер + версия + модель + площадка, свой счёт у каждой.
- Минимум 3 ячейки + бейзлайн без LLM. Сравнение после комиссий, на одних и тех же сигналах.
- Модели выбираем по своей арене, внешние лидерборды — только ориентир.

### 6.10 Улучшатели (по расписанию, не в торговом цикле)
- Post-Trade Reviewer: разбор каждой закрытой сделки → запись в БД, итог дня в Т5.
- Strategy Researcher (раз в неделю): паттерны ошибок → предложение правки карточки (новая версия).
- Shadow Evaluator: новая версия работает в тени рядом со старой; замена — только после победы после комиссий и подтверждения Германа.
- Улучшатели не трогают риск-лимиты.

### 6.11 Надзор
- **Сторож (код, отдельный процесс):** kill-switch (флаг в `limits.yaml` или файл `engine/KILL_SWITCH`), проверка связи с площадкой, позиция без стопа → закрыть, расхождение позиций БД и биржи → пауза и алерт, дневной лимит у края → стоп новых входов.
- **Hermes:** расписания, перезапуски, лимиты LLM.
- **Heartbeat:** движок раз в минуту пишет «жив»; нет сигнала 5 мин → алерт в Т2.

### 6.12 Telegram-управление (через Hermes)
- Автоматически: сигналы, решения с обоснованием, сделки, итог дня, предложения улучшателей, алерты сторожа.
- Команды: `/status`, `/pause`, `/resume`, `/kill`, `/why <id>`, `/context <текст/скрин>` (→ `clusters/<имя>/inbox.md`), `/rule <правка>` (→ новая версия в тени).
- `/kill` срабатывает без LLM (файл KILL_SWITCH) и подтверждается ответом.

## 7. Контракты (JSON Schema в `shared/contracts/`, pydantic для Python, zod для TS)

**signal.v1** — выход детектора:
`signal_key, cluster, version, symbol, venue_data, timeframe, side, entry, sl, tp[], rr, setup{sweep_time, choch_time, fvg_time, fvg_low, fvg_high}, created_at, expires_at, image_ref, status`.

**decision.v1** — выход мозга:
`signal_key, action (TAKE | SKIP | HOLD), confidence 0–1, reasons{context, setup, risks}, model, prompt_version, latency_ms`. Уровни в решении не передаются: их берём из сигнала.

**order_intent.v1** — выход риска для исполнения:
`signal_key, venue, side, qty, entry, sl, tp[], leverage, risk_usd, client_order_id, risk_action (APPROVE | REDUCE), reasons[]`.

Все числа — строки Decimal. Версия контракта меняется при любом несовместимом изменении.

## 8. Данные и БД

Одна PostgreSQL на дневник и агентов, владелец схемы — Prisma (`shared/db`), Python ходит через SQLAlchemy Core по сгенерированным определениям (решение 11.10). Детали — `shared/DATA_ARCHITECTURE.md`. Движок пишет под ролью `tp_engine` с минимальными правами: в профили пропов и лимиты — только чтение.

### 9.1 Почему не берём готовый фреймворк ядром
- У нас уже есть то, что фреймворки делают по-своему: риск-слой с профилями пропов, общая БД с дневником (Prisma, fills как единица правды), LLM-петля через Hermes. Встраивание в freqtrade или Nautilus = переписать это под их модель данных.
- freqtrade (GPL-3.0) — заточен под «стратегия-класс + свой бот», плохо ложится на «LLM решает по сигналу + проп-лимиты».
- Nautilus Trader (LGPL-3.0) — сильный, но тяжёлый (Rust + Cython); оправдан при десятках инструментов и HFT, нам пока избыточен. Вернёмся, если упрёмся в скорость или сложность исполнения.
- Итог: свой тонкий движок + библиотеки. Фреймворки — образец архитектуры и сверка результатов бэктеста.

## 10. Нефункциональные требования
- **Надёжность:** любая ошибка → не торговать (fail-closed). Перезапуск движка не дублирует ордера.
- **Задержка:** от закрытия свечи до ордера ≤ 5 мин (Hermes на Mac); при переезде на сервер — ≤ 30 с.
- **Наблюдаемость:** структурные логи (JSON), heartbeat, итог дня, алерты в Telegram.
- **Тесты:** риск — 100% правил; детектор — фиксированная история → те же сигналы; адаптеры — на демо; бэктест — сверка с jesse/freqtrade на одной стратегии MA-cross.
- **Воспроизводимость:** каждый прогон хранит версию кода (git hash), конфиг, модель и промпт.
- **Среда:** сейчас Mac (молчит, когда Mac спит) → сервер, когда нужна торговля 24/7 (до P5 обязательно).

## 11. Безопасность
- Секреты только в `.env` (в .gitignore), в чат не присылать (случай 11.10). Архив Hermes вырезает сообщения с ключами.
- Ключи бирж: торговля без вывода, по возможности — привязка к IP сервера.
- Hyperliquid: отдельный agent wallet с правом торговли, основной ключ в систему не попадает.
- Роль БД `tp_engine` не может менять лимиты и профили.
- Kill-switch работает без LLM и без сети к LLM.

## 12. Метрики и критерии перехода (предложение — утверждает Герман)

**Бумага → демо (P2 → P4):** форвард-тест ≥ 4 недель и ≥ 50 сигналов; полный след у 100% сигналов; ни одного нарушения лимитов в симуляции.

**Демо → проп (P4 → P5):**
- ≥ 100 сделок на демо по API;
- после комиссий: PF ≥ 1,3, средний R > 0;
- макс. просадка ≤ 50% от лимита выбранного пропа;
- LLM-фильтр не хуже бейзлайна без LLM (иначе на проп идёт бейзлайн);
- ноль случаев «позиция без стопа» и расхождений позиций, не пойманных сторожем;
- профиль пропа сверен с T&C, поля без `null`;
- движок на сервере, работает 24/7;
- проверены правила подписки Claude на автоматизацию или переход на API.

## 13. Этапы и критерии готовности

**P1 — детектор готов к БД** (Т1, ~1 неделя)
- Время вместо номеров свечей; ключ сигнала; статусы сигналов в live.
- Стабильность времени закрытия свечи MEXC между прогонами.
- R и R после комиссий в истории; модель комиссий.
- Сверка со `smart-money-concepts` на тех же 14 днях — отчёт о расхождениях.
- Готово, когда: перепрогон истории даёт те же ключи; тесты детектора зелёные.

**P2 — бумажная торговля** (~1–2 недели + 4 недели форварда)
- Каждый сигнал → решение Hermes (TAKE/SKIP) → риск → paper-адаптер с профилем demo → исполнение по живым свечам.
- Параллельно бейзлайн без LLM.
- Журнал в JSONL до P3.
- Готово, когда: у каждого сигнала есть след «сигнал → решение → риск → результат»; итог дня в Т5.

**P3 — общая БД** (после J0 дневника)
- Детектор, решения и риск пишут в PostgreSQL; история перепрогоняется в БД; дневник показывает сделки агентов.

**P4 — демо-исполнение и арена** (4–8 недель)
- Адаптер Hyperliquid testnet или OKX Demo (через ccxt), Order Manager, Сторож, heartbeat.
- MA-cross как второй кластер и бейзлайн; арена ≥ 3 ячеек.
- Свой бэктест сверен с jesse/freqtrade на MA-cross.
- Переезд движка на сервер.

**P5 — проп**
- Выбор пропа (Propr или HyroTrader), сверка T&C, профиль без `null`.
- Propr Beta → челлендж минимального размера с kill-switch.
- Только после критериев §12 и подтверждения Германа.

**P6 — улучшатели и тени**
- Post-Trade Reviewer, Strategy Researcher, Shadow Evaluator, Promoter.

## 15. LLM и стоимость
- Сейчас все роли выполняет Hermes на подписке Claude Max, отдельного API нет. Opus 5.5 — решение, Sonnet 5.5 — массовые роли (при переходе на API). Бесплатные модели OpenRouter — черновые прогоны.
- Минимальный мозг: 1 вызов на сигнал. Полный: ~6 вызовов (5 Sonnet + 1 Opus). 3 кластера × ~10 сигналов/день ≈ 30–180 вызовов/день.
- Переход на API и сервер — при упоре в лимиты подписки, нужде в 24/7 или > 3–4 ячейках арены. Стоимость каждого вызова пишется в `llm_calls`.
