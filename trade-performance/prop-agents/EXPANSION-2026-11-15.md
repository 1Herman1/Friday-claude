# Дополнение к ТЗ: наблюдение рынка, арбитраж, управляющий и SMC

Дата: 2026-11-15 MSK. Источник: решение Германа в Т1 (thread 30). Статус: требования зафиксированы, реализация изолированных read-only модулей в работе. Это НЕ разрешение на реальные заявки, выводы или переключение действующего SMC-monitor.

## Уточнение владельца 15.11.2026: живая витрина и altcoin funding

- Нужна **живая панель процесса**, а не набор итоговых HTML-отчётов: текущий этап, реальные события и длительности, входящие данные, кандидаты, причины отказов, состояние источников/ролей. Поверхность Monitor, графитовая консоль с тёплым оранжевым акцентом по присланному референсу, без копирования бренда и декоративных выдуманных метрик.
- Первая реализация — отдельная страница `/agents-monitor` внутри существующего дневника, read-only API, обновление представления каждые 5 секунд, возраст данных отдельно от частоты UI. Не подключённые news/LLM/executor честно «не подключено». Обновление часов/страницы не выдаётся за новый API-снимок. Пауза просмотра не останавливает collector и не является kill-switch.
- Фокус арбитража меняется с демонстрационных BTC/ETH на **поиск экстремального funding по всему доступному altcoin-universe нескольких бирж**, с интересом к низколиквидным инструментам. BTC/ETH остаются контрольными, не ограничением. Доступные публичные источники-кандидаты: BingX, Bitget, Gate, Binance, OKX; реальное покрытие и ошибки подтвердит запуск, это не список разрешённых торговых аккаунтов. MEXC/Bybit не возвращаются в торговлю в обход ограничений аккаунта.
- Ставки порядка **1–2% за расчётный интервал** — фильтр наблюдения, не обещание, что такие ставки всегда присутствуют или сохранятся. Показать знак, интервал, время следующего расчёта и время получения. Положительный funding платят long → short, отрицательный short → long; выбирать направление только с учётом обоих знаков и времени начислений. Нет интервала/времени — UNKNOWN, не fallback 8h.
- Целевая пара — одинаковый базовый актив и сопоставимые linear USDT perpetual, short там, где нормализованная ставка выше, long там, где ниже. Разность текущих ставок на общий горизонт — **индикативный carry**, не зафиксированная выплата и не net PnL. Платёжный календарь двух ног рассчитывается отдельно, не обещать синхронное получение.
- Низкую ликвидность измеряем глубиной/спредом/доступным объёмом под заданный размер. «Не BTC» не равно «низколиквидная». Наличие высокой ставки не разрешает ордер при отсутствии второй площадки, глубины, известных fees, правил закрытия и маржинального запаса. При росте basis одна нога может ликвидироваться, несмотря на встречную позицию на другой бирже.
- **CoinGlass — допустимый источник поиска, не единственная правда для исполнения.** Официальный endpoint `/api/futures/funding-rate/exchange-list` возвращает текущую ставку, текущий interval и next funding time по биржам; percentage units, не decimal fraction. Документация указывает обновление каждые 20 секунд и отсутствующие поля для части бирж. API использует тариф/ключ; покупку не совершать, ключ не просить в чате. Бесплатная веб-витрина не означает бесплатный программный API. Пока нет подключения, панель показывает «CoinGlass не подключён» и использует прямые публичные API.
- CoinGlass discovery → проверка metadata/ставки/интервала непосредственно на бирже → свежие два стакана и объём → все расходы обеих ног/закрытия → quant/risk → бумажное сопровождение. Автоматическая торговля/переводы этим уточнением не включены.
- Важно показать notional на каждой ноге и общий требуемый капитал/маржу; ставка от notional не равна доходности на суммарный капитал стратегии.

Первичные источники уточнения: https://docs.coinglass.com/reference/fr-exchange-list ; https://docs.coinglass.com/reference/endpoint-overview ; https://www.coinglass.com/pricing ; https://bingx.com/en/support/articles/14857605906575 . Документация CoinGlass прочитана в браузере 15.11.2026; API без ключа не объявляется подключённым.

## 1. Изменения области проекта

- Добавляем общий сканер всех доступных USDT perpetual BingX: цена, памп/дамп, объём, funding, open interest; количественные показатели покрытия и отказов обязательны. «Все монеты» в MVP = активные USDT perpetual, не автоматическое обещание покрытия spot/TradFi и всех контрактов без данных.
- Внешние биржи — источники публичных trades/orderbook/funding/OI для сопоставления. Первая межбиржевая проверка: BingX/Bitget, BTC/ETH одинакового вида контракта. Доступность API не означает доступность торговли для владельца аккаунта.
- Исследование/бумажная проверка арбитража включаются в общую платформу; отдельный кластер и изолированный капитал. Арбитраж НЕ автоматически разрешён на проп-счетах. Ранее исключённый из prop-agents арбитраж теперь входит как отдельный исследовательский модуль своих счетов.
- Новости, макро и фундаментальные события обязательны: прежнее предложение исключить фундаментал отменено владельцем. Корпоративный DCF/P/E не подставляем вместо крипто-/макроанализа.
- Управляющий менеджер обязателен: собирает данные ролей, формирует TAKE/SKIP/HOLD и объяснение. Исполнение только кодом после quant/risk gates.
- Визуальная панель: живая витрина процесса внутри раздела «Агенты» дневника, по референсу владельца; отдельные статичные отчёты остаются дополнительным экспортом, не заменой мониторинга.

## 2. Принципы данных и аномалий

Каждое наблюдение: venue, market_type, canonical instrument, exchange timestamp, received_at, endpoint, freshness, coverage. Не смешиваем spot/perp, линейные/обратные контракты, единицы OI или токены с одинаковыми тикерами. Источник и исходный ответ сохраняются без ключей.

Аномалии: изменение цены на фиксированных горизонтах, относительный объём к собственной истории, изменение OI с известными единицами, funding с периодом начисления, дисбаланс агрессивных buy/sell сделок, крупные принты относительно ликвидности. Один 24h snapshot не доказывает историческую аномалию; без baseline статус WARMUP/UNKNOWN. Наличие OI не означает наличие его истории.

«Крупные покупки»: совокупная агрессия покупателей по публичным сделкам, не доказательство личности кита или накопления одним кошельком. У каждой сделки есть покупатель и продавец. Видимый стакан может быть снят без исполнения. On-chain-перевод на биржу не доказывает продажу. Не приписывать неизвестную направленность/личность.

Фрагменты диктовки «по Фогу», «Omalley», «Wergini Букчина» сохранить как нерасшифрованные. Не считать их выбором продукта/платной подписки/сети.

## 3. Арбитраж: проверяемая экономика

Раздельные стратегии:
1. Межбиржевой spot: покупка по ask на дешёвой площадке и одновременная продажа заранее имеющегося актива по bid на дорогой.
2. Perp/perp: одинаковый базовый актив, противоположные позиции, риск basis/маржи/ликвидации и изменения funding.
3. Spot/perp cash-and-carry: спот и противоположный perp; funding не гарантирован и может сменить знак.

В MVP только публичные GET и расчёт indicative spreads. Не включаем автоматические переводы. Для быстрого двухстороннего исполнения средства/активы заранее размещаются на обеих площадках; перевод — отдельная перебалансировка, не часть гарантированно мгновенной сделки.

Чистый результат: исполнимая выручка минус исполнимая покупка, все комиссии входов/выходов, проскальзывание по объёму стакана, funding/borrow, ребалансировка и резерв на задержку. Последняя цена/картинка спреда не исполнимая цена. Неизвестный тариф аккаунта = HOLD, а не нулевая комиссия. Funding сравнивается на общем горизонте только при известных интервалах.

Будущий исполнитель: уникальный intent/idempotency, предварительная проверка балансов и торговли инструментом, две ноги с ограничением max unhedged exposure/time, partial fills/cancel/reject, аварийный hedge/unwind, сверка фактических fills, журнал чистого результата. Две CEX заявки не атомарны. LLM не ставим в низколатентный путь: он выбирает режим/объясняет, исполнение deterministic.

Готовое решение-кандидат: Hummingbot (reference/reuse, не объявлен установленным или готовым заработать). Официально есть arbitrage executor и funding-rate script; connector BingX в опубликованном списке Spot, что не подтверждает поддержку BingX perpetual. Перед внедрением проверить лицензии, текущие connectors, совместимость и paper mode. Чужой README «production-ready» не доказательство надёжности или прибыли.

## 4. Quant gate и risk gate

Существующий риск-менеджер: `engine/risk.py`, Python-код, не LLM. Он считает размер и ограничивает equity drawdown/дневной убыток/позиции/серию потерь, проверяет whitelist, разрешение автоматизации, stop, RR, kill-switch. Наличие модуля не означает включённый API-исполнитель. Известный технический долг: денежные float в risk.py вместо общего Decimal-контракта; лимиты не меняем автоматически.

Quant gate: отдельный кодовый допуск исследования/сигнала, не замена risk.py. Версия, рынок, период, источник, coverage, комиссии/funding/slippage обязательны. Раздельно development, holdout и forward; sample adequacy и пороги конфигурируются явно. Отсутствующие/невалидные данные = HOLD. Отрицательное after-cost ожидание, плохая глубина или устаревшая котировка = запрет согласно policy. Не переучиваем параметры на holdout. Логируем каждый отказ.

Управляющий/LLM не может отменить REJECT/HOLD, менять риск-лимиты, суммы, стопы или разрешать площадку. News-тезис не оправдывает расширение стопа/усреднение. Последний риск-чек выполняется непосредственно перед исполнением.

## 5. Новости/фундаментал: факты отдельно от объяснений

Вход: календарь FOMC/Fed, CPI/занятость BLS и другие первичные релизы; новости бирж/регуляторов/проектов, ликвидации и подтверждённые on-chain события. Данные храним с published_at и received_at; учитываем пересмотры. «Выше ожиданий» допустимо только при сохранённом опубликованном ДО релиза консенсусе; без поставщика консенсуса поле UNKNOWN.

Выход: событие + первоисточник + время, факт/ожидание/предыдущее, вероятный механизм, альтернативные объяснения, влияние на наш сетап, уверенность. Постфактум совпадение новости и движения не объявляем доказанной причиной. Пример владельца «BTC упал сегодня на 10%» — гипотетический пример, не проверенный факт текущего дня. Новости могут привести к SKIP/HOLD, но не отменяют риск.

## 6. Управление и визуализация

Поток: market scanner → detector → quant eligibility → роли контекста/новостей → управляющий TAKE/SKIP/HOLD → deterministic risk → paper executor → fills/reconciliation/journal.

Режимы PAPER / APPROVAL_REQUIRED / AUTO — отдельные настройки аккаунта, не догадка по тексту. Сейчас новые компоненты только PAPER/read-only. Последнее сообщение допускает ручное подтверждение, но не выбирает его однозначно вместо ранее согласованной автономии; перед реальной торговлей владелец выбирает режим и лимиты. Нажатие «подтвердить» в Telegram требует проверки owner user ID, подписи intent/срока действия, повторного risk-check и защиты от повторного исполнения. Само наличие кнопки не даёт полномочий.

Панель показывает coverage/staleness, baseline warmup, anomaly evidence, spread gross/net/unknown, состояние ног и общий риск, причины TAKE/SKIP, версии и kill-switch. Стилизация не подменяет реальные данные.

## 7. SMC: текущая и исследуемая версия

Факт: `CARD-v0.3.md` и `v03_preview.py` уже существуют как изолированный preview 1h sweep → 15m IFVG. Он не является прибыльным бэктестом и не включает утверждённый HTF-фильтр. Live v0.1 не переключаем. Название «0.3.3» из диктовки не подтверждает существующий релиз; новая работа — audit v0.3, не переименование.

Последний запрос предварительно трактуем как ДВА исследования:
- A: контекст 1h → sweep 15m → IFVG вход 5m.
- B: контекст 4h → sweep 1h → IFVG вход 15m.

Противоречие «на пятиминутках»/«на 15 минут» отмечено; не запускать production на основании этой трактовки. HTF trend должен быть формально определён до честного бэктеста (структура или конкретная MA, это пока не согласовано). Доступность 4h данных не равна применению контекстного фильтра.

Стоп за крайним фитилём excursion снятия, не за IFVG; точный tick-rounded buffer должен быть явно указан. TP1=2R, TP2 следующая ликвидность/имбаланс; доля 50% и BE — ранее предложенные параметры, отдельно указывать их статус. Несколько ярлыков ликвидности на одной свече не равны независимым сделкам.

Отчёт: один кандидат/исполненная сделка на строку, уровень и время его известности, sweep, IFVG, контекст, entry timestamp закрытия, excursion/SL, TP, причины пропуска, занятость позиции, все fills/costs, gross/net R и chart. Разделять обнаружено, подтверждено, исполнимо, LLM принято, реально доставлено. Отсутствующий HTF контекст = production ineligible.

Стоимость в R = сумма фактических комиссий и отдельно проскальзывания / исходный денежный риск. Старый `cost_R` v0.2 оценивал taker-round-trip, а не фактическую стоимость каждой сделки; прежнюю фразу «комиссия съедает −0.35R» не выдавать за измеренный тариф BingX. Статистику v0.2 сначала аудировать: причинность, IFVG, execution ambiguity, drawdown base, временные окна/DST и артефакты запуска. Ошибки реализации не доказывают отсутствие преимущества у всей SMC.

## 8. Приёмка и следующие ворота

- Read-only MVP: реальный публичный snapshot, известное покрытие, неизвестные поля явно UNKNOWN; без заявок/секретов/переводов.
- Quant gate: отдельные тесты fail-closed и обоснованные решения, интеграция в executor отмечается отдельно.
- SMC audit: воспроизводимый прогон сохранённых свечей, CSV по кандидатам/пропускам, независимый replay. Не обещать доходность при отсутствующих данных/правилах.
- Paper: накопление исторических baseline, моделирование двух ног и fees, сравнение с простой стратегией без LLM; затем демо API после выбора режима/лимитов и проверки правил площадок.
- Live: отдельное явное решение владельца; withdrawal permissions не нужны и не запрашиваются.
