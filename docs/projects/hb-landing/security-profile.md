# Профиль безопасности: hb-landing

Карта стека для агентов `security-*`. Универсальные классы уязвимостей — в
`docs/core/anti-patterns/security.md`; здесь только то, как эти классы
выглядят в hb-landing.

Проверено чтением: `hb-landing/package.json`, `hb-landing/astro.config.mjs`,
`hb-landing/.gitignore`, `hb-landing/src/`, `hb-landing/public/`,
`docs/projects/hb-landing/project.md`.

---

## Стек

| Слой | Чем реализовано |
|---|---|
| Язык / рантайм | TypeScript strict, сборка Node.js только на этапе `astro build` |
| Серверный фреймворк | Нет. Astro 5, `output: "static"` — результат сборки чистая статика (HTML/CSS/JS), рантайм-сервера в проде нет |
| Клиент | Astro-компоненты + минимум JS (диалог контактов, lazy-видео); Tailwind 4 через `@tailwindcss/vite` |
| База и доступ к ней | Нет. Контент кейсов — типизированный файл `hb-landing/src/content/cases.ts`, компилируется в статику |
| Хранилище файлов | Нет внешнего. Медиа лежит в репозитории: `hb-landing/src/assets/cases/*.jpg` (обрабатывает `astro:assets`/sharp на сборке), `hb-landing/public/media/banner/` (копируется в `dist/` как есть) |
| Аутентификация | Нет. Личных кабинетов, форм входа, сессий не существует |
| Хостинг и выкатка | Любой статический хостинг из `dist/` — конкретный провайдер **требует уточнения** (project.md: «решается отдельно») |
| Фоновые задачи | Нет |
| Платежи | Нет. Контакты — прямые `tel:` / `mailto:` / `t.me` ссылки, отправки данных на сервер нет |

Чего в проекте нет (чтобы агенты не искали): Next.js, React-SPA, Vercel-specific
API routes, NextAuth, Zustand, React Router, БД любого вида, ORM, форм с
`action`/`onSubmit` на сервер, `fetch()` к своему или чужому API, внешних
`<script src>`, счётчиков аналитики (`googletagmanager`, `mc.yandex`), OAuth,
вебхуков, файловой загрузки от пользователя, `.env` с реальными значениями.

Подтверждено grep по `hb-landing/src` и `hb-landing/public`: ни `<form`, ни
`fetch(`, ни `<script src`, ни `googletagmanager`/`mc.yandex`, ни
`import.meta.env` не встречается.

## Где что лежит

| Что | Путь |
|---|---|
| Страницы/секции | `hb-landing/src/pages/**`, `hb-landing/src/components/**` (структура — уточнить при следующей задаче, не обязательна для профиля) |
| Контент кейсов | `hb-landing/src/content/cases.ts` |
| Токены дизайн-системы | `hb-landing/src/styles/global.css` (блок `@theme`) |
| Статические ассеты, копируемые как есть | `hb-landing/public/**` (в т.ч. `public/media/banner/`) |
| Изображения, обрабатываемые сборкой | `hb-landing/src/assets/cases/*.jpg` через `astro:assets` |
| Конфигурация сборки | `hb-landing/astro.config.mjs` |
| Секреты | Отсутствуют по назначению: сайт статический, серверных ключей нет. `.env`/`.env.local` в `.gitignore`, но фактически не используются |

## Перевод классов в конкретику

| Класс (см. `anti-patterns/security.md`) | Что искать здесь |
|---|---|
| §1–2 Аутентификация, сессии, токены | Неприменимо: логина, аккаунтов, сессий на сайте нет |
| §3 Доступ без проверки владельца / роли | Неприменимо: нет пользователей и ресурсов с владельцем — весь контент публичный по замыслу |
| §4 SQL/NoSQL/шаблон-инъекции | Неприменимо: нет БД, нет серверного шаблонизатора, исполняющего пользовательский ввод. Astro-шаблоны компилируются статически из собственного контента разработчика, не из пользовательского ввода |
| §5 Сырой HTML / XSS | Применимо частично: искать `set:html` в `.astro`-файлах — это единственный способ вставить сырую разметку в Astro. Источник разметки — только собственный контент (`cases.ts`, компоненты), не ввод посетителя, поэтому классического XSS от третьих лиц канал не открывает. Проверять при каждой правке контента |
| §5 Заголовки безопасности (CSP, X-Frame-Options, HSTS) | Приложение их не ставит — не может, сервера нет. Их обязан выставить статический хостинг (через `_headers`/`netlify.toml`-аналог, правило Nginx или настройку CDN — конкретно зависит от выбранного хостинга, который пока не определён). Записать в чек-лист выбора хостинга и проверить после деплоя `curl -I` на боевом домене |
| §6 CSRF | Неприменимо: нет кук, нет сессий, нет изменяющих запросов к своему серверу |
| §6 CORS | Неприменимо: нет собственного API, которому нужна политика CORS |
| §7 Загрузка файлов | Неприменимо: форм загрузки нет. Файлы в `public/media/` и `src/assets/` — только те, что кладёт в репозиторий сам автор, не посетитель сайта |
| §8 SSRF / внешние запросы | Неприменимо: код не делает запросов по URL, полученному от пользователя, и вообще не делает серверных запросов в рантайме (рантайма нет) |
| §9 API | Неприменимо: собственного API нет |
| §10 Вебхуки | Неприменимо: входящих вебхуков нет |
| §11 Платежи и бизнес-логика | Неприменимо: платежей, купонов, лимитов нет |
| §12 Гонки | Неприменимо: нет конкурентного состояния — весь сайт read-only статика |
| §13 Секреты | Применимо как проверка отсутствия: убедиться, что `.env`/`.env.local` не закоммичены (в `.gitignore` есть), что в `astro.config.mjs`, `package.json`, `src/content/cases.ts` нет ключей API. На момент проверки — секретов не найдено, и по стеку их и не должно появиться, пока сайт статический |
| §15 Криптография / HTTPS | Применимо: сайт обязан отдаваться только по HTTPS с редиректом с HTTP — это настройка хостинга, не кода. Проверить после выбора хостинга |
| §16 Цепочка поставок | **Главный применимый класс.** Прямых зависимостей шесть: `astro`, `@tailwindcss/vite`, `tailwindcss`, `@fontsource-variable/montserrat`, `@fontsource-variable/open-sans`, `sharp` — плюс их транзитивные деревья. `sharp` собирает нативные биндинги при установке (`npm install` может выполнять postinstall-скрипты) — единственное место, где сборка исполняет сторонний код. Версии зафиксированы `package-lock.json`. Проверять `npm audit` регулярно, особенно после обновления `sharp` и `astro` (мажорные версии часто) |
| §17 Конфигурация и инфраструктура | Применимо частично: «база данных слушает наружу» и т.п. неприменимо (нет процессов), но «листинг директорий», «резервные копии в доступном месте», «служебные каталоги по вебу» — применимо к результату деплоя: в `dist/` не должно попасть ничего лишнего (см. раздел «Целостность dist/» ниже) |
| §18 Парсеры/десериализация | Неприменимо: пользовательский ввод не парсится (XML, YAML и т.п. на входе нет) |
| §19 OAuth | Неприменимо |
| §22 Лимиты (техническое) | Неприменимо к приложению: нет эндпоинтов, которые можно заDDoS-ить логикой. Общий rate-limit/защита от флуда — на уровне CDN/хостинга, вне кода проекта |
| §23 Утечки через ошибки | Частично применимо: Astro в dev-режиме может показывать подробные оверлеи ошибок — они не должны попасть в прод-сборку (`astro build` их не включает по умолчанию, но стоит перепроверить на боевом URL, что 404/500 хостинга не палят версию сервера/фреймворка) |

## Целостность `dist/`

- `astro build` компилирует `src/pages/**`, `src/components/**`,
  `src/content/cases.ts` и обрабатывает изображения из `src/assets/cases/*.jpg`
  через `astro:assets` (использует `sharp`).
- Содержимое `hb-landing/public/**` (включая `public/media/banner/`)
  копируется в `dist/` **без изменений и без обработки** — что положено в
  `public/`, то и окажется публично доступным по прямому пути. Перед деплоем
  проверять, что там нет черновиков, служебных файлов, `.git`, дампов.
- В `dist/` не должно быть исходников `.astro`/`.ts`, `package.json`,
  `.env*` — Astro их и так не копирует, но стоит перепроверить после
  обновления версии Astro.

## Защита, встроенная в стек

| Риск | Закрыто стеком | Что всё равно проверять |
|---|---|---|
| XSS через шаблон | Astro экранирует интерполяцию `{}` в `.astro`-шаблонах по умолчанию | Использование `set:html` — единственный обход экранирования |
| SQL/NoSQL-инъекции | Неприменимо — нет БД | — |
| Утечка серверных секретов в клиентский бандл | Неприменимо — нет серверных секретов, `import.meta.env` в коде не используется | Появление `.env`-переменных в будущем — проверить префикс `PUBLIC_` перед использованием в клиентском коде |

## Команды проверки

```bash
cd hb-landing
npm audit                     # уязвимости в зависимостях (их всего 6 прямых)
npm run build                 # сборка + проверка типов (Astro TypeScript strict)
```

Тестов (`npm test`) в проекте нет — не заявлены в `package.json`.

## Доступ к боевому серверу

| Что | Как |
|---|---|
| Выполнить команду на сервере | Требует уточнения — хостинг не выбран |
| Логи | Требует уточнения — зависит от хостинга (обычно логи статического хостинга ограничены access-логами CDN) |
| Домен боевого сайта | Требует уточнения |
| Домен тестового стенда | Требует уточнения |

Рантайм-проверки из `docs/core/security-runtime.md` (заголовки, HTTPS,
листинг директорий) можно и нужно прогонять внешне (`curl -I` на публичный
домен) сразу после выбора хостинга, без доступа внутрь — сервера в
классическом смысле здесь нет.

## Известные и принятые риски

| Риск | Почему принят | Пересмотреть |
|---|---|---|
| Заголовки безопасности (CSP, HSTS, X-Frame-Options) не выставляет приложение | Ставить их некому внутри кода — сайт статический, заголовки задаёт хостинг/CDN | Сразу после выбора хостинга — сверить фактически отдаваемые заголовки `curl -I` по чек-листу §5 |
| Хостинг и способ деплоя не определены | Решается отдельно (project.md) | Как только выбор сделан — дополнить разделы «Хостинг», «Доступ к боевому серверу» этого профиля |

## Условие пересмотра профиля

Этот профиль верен только пока сайт статический и без обратной связи с
сервером. Он **обязателен к пересмотру целиком**, как только появится любое
из:

- форма обратной связи с отправкой данных (на свой бэкенд или сторонний
  сервис — Formspree, Telegram Bot API и т.п.);
- любой `fetch()`/XHR с клиента к какому-либо API;
- счётчик аналитики или пиксель (Yandex.Metrika, GA, рекламные пиксели);
- встраивание стороннего виджета (чат, форма бронирования, карта с внешним
  скриптом).

Любое из этого сразу означает: появляются персональные данные (минимум —
email/телефон посетителя), нужно согласие на обработку, нужна политика
конфиденциальности, почти наверняка нужен cookie-баннер — то есть должен
параллельно обновиться и правовой контур в `project.md`, и профиль
дополниться разделами §1, §6 (CORS), §9 (API), §13 (секреты сервиса), §17
(куда уходят данные). До этого момента перечисленные классы неприменимы не
по недосмотру, а потому что канала для них физически нет.
