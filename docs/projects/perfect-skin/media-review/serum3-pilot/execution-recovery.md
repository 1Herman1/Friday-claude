## 126 is a quote, NOT a provider billing ceiling

The fixed request remains one `kling/v2-5-turbo-image-to-video-pro` job with string duration `10`, the fixed prompt and two approved frame URLs. The runner requires the unique exact public quote **126 credits / USD0.63** before uploads, then rechecks immediately before the only create POST. Ranges, duplicates, changed price/model/duration and quote >126 all fail closed. This deliberately also rejects a changed lower quote pending review; no automatic model/settings fallback exists.

The current official create schema at <https://docs.kie.ai/market/kling/v25-turbo-image-to-video-pro.md> exposes `model`, `callBackUrl`, and `input`, not a documented per-task maximum-cost/reservation parameter. No provider-side ceiling is implemented or claimed. Balance >=126 checks availability, not the maximum possible charge. `quotedCredits:126` and `providerBillingCap:false` replace misleading `maxCredits` metadata. The residual price/billing race after the final quote check cannot be removed locally. If the parent requires a literal hard126 limit, payment remains blocked until a documented provider/account-side control is available or the owner accepts quote-based expected cost rather than a ceiling. Do not automatically run a paid job to investigate billing.

A reported charge >126 is preserved as `billingViolation:true`; retrieval still saves and decodes the already-paid output, then the CLI fails visibly for reconciliation. It never creates another job to compensate. Numeric billing data must remain finite, nonnegative integers for this fixed-credit pilot.

## Submission and independently retained receipt

The Actions `generate-one` CLI now performs **submission only**. It writes exclusive mode0600 `task-receipt.json`, fsyncs it, then emits only the validated task ID to the Actions output and summary. The next pinned `upload-artifact` step publishes `serum3-task-receipt-<run-id>` with requested 90-day retention **before polling begins**. Actual retention is subject to repository limits. Receipt fields are task ID, original run ID/SHA, fixed model/duration, quote, billing-cap false and submitted state; no key, raw response, upload/download URL or prompt is included. The original summary provides a second recovery handle.

A receipt upload failure does not authorize a new create. Read-only retrieval still executes when the submit step returned its validated task ID, even after receipt persistence/upload failure, to preserve the paid output. If the runner is lost between provider acceptance and receipt publication, durable evidence may be absent; this is not a provider transaction or atomic cross-system guarantee. An ambiguous create timeout with no returned task ID requires provider-history reconciliation, never blind resubmission.
