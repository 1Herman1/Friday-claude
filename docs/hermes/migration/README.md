# Перенос Hermes на постоянно доступный хост

Обновлено: 13 ноября 2026. Статус: локальная подготовка выполнена; целевой хост не указан, удалённый перенос НЕ выполнен. Работа относится к активному профилю default; остальные профили не изменяются.

## Что уже проверено

- На исходном Mac: Hermes Agent v0.23.1+1205.g40ba2d4, Python среды Hermes 3.14.9. Это результат локального `hermes --version`, не утверждение о последней версии в интернете.
- Проверены локальные `hermes backup --help`, `hermes import --help`, `hermes gateway install --help`. Доступны экспорт/импорт и установка Linux system service с явным пользователем.
- Создан quick snapshot `20261113-160114` в `~/.hermes/state-snapshots/`. Снимок содержит 23 файла; SQLite quick_check для четырёх баз вернул `ok`.
- В установленной версии `hermes backup --quick --output ...` создал именно snapshot, а не ZIP по заданному пути. Не выдавать этот снимок за полный переносимый архив: полный экспорт — отдельная операция.
- Снимок хранится локально, содержит секреты и НЕ прикладывается в Telegram и НЕ добавляется в Git. Каталог снимка имеет права 0700.
- Проверено существование внешних данных: `~/Friday-claude`, `~/Library/Application Support/trade-performance/pg17`, `~/Applications/Postgres.app`. Наличие файла/каталога не доказывает работоспособность БД или сервисов.

Официальная документация рекомендует для переезда на другую машину `hermes backup` и `hermes import`; это не то же самое, что быстрый снимок перед обновлением.[1][2]

## Что нужно от владельца

1. Хост уже есть или нужно подобрать: VPS / выделенный сервер / удалённый компьютер.
2. Если есть — адрес, ОС и имя пользователя. Пароли/приватные ключи не передавать сообщением; доступ выдаётся через безопасный канал или существующий SSH-ключ.
3. Определить объём: только основной Hermes и студийные проекты либо также дневник, PostgreSQL и торговые расписания. Второе не переносится автоматически вместе с конфигурацией Hermes.
4. Выбрать окно переключения: краткая остановка старого gateway нужна для исключения конкурирующих экземпляров и повторного исполнения расписаний.

Покупка/аренда, выбор тарифа и открытие публичных портов пока не выполнялись. Рекомендация по ресурсам и расходам должна исходить из выбранного объёма, а не обещания одной универсальной конфигурации.

## Последовательность переноса

### 1. Инвентаризация и точка восстановления

Уточнить активный профиль, версию, плагины, skills, расписания, внешние скрипты и зависимости. Отдельно учесть репозиторий, незакоммиченные/неотслеживаемые рабочие материалы, клиентские ассеты и БД. Не считать GitHub резервной копией игнорируемых данных.

Перед финальным экспортом сделать согласованную копию актуального состояния; определить состав полного архива по фактической версии Hermes. Не копировать работающую SQLite простым файловым копированием с игнорированием WAL. Хранить архив с секретами только в закрытом локальном каталоге; передача — по защищённому каналу, не через публичную ссылку.

### 2. Подготовка хоста

Создать отдельного непривилегированного системного пользователя и защищённый SSH-доступ. Установить совместимую версию Hermes и зависимости заново: macOS-виртуальное окружение не переносить как Linux-окружение. Не совмещать миграцию с необязательным обновлением и сменой модели.

Восстановить данные и проверить импорты без запуска Telegram gateway и расписаний. Исправить абсолютные пути `/Users/...`, платформозависимые команды и внешние интеграции. Авторизацию моделей проверить отдельно: скопированный auth-файл сам по себе не доказывает работоспособность OAuth на новом хосте.

### 3. Пробный запуск без дублирования

Проверить модель реальным коротким запросом от владельца, чтение разрешённого тестового файла, сохранение состояния, доступ к репозиторию и восстановление истории. Не отправлять тестовые торговые действия и не запускать платёжные операции.

Проверить каждую нужную задачу расписания отдельно; повторные инстансы на старом и новом хосте не должны одновременно выполнять одну задачу. Telegram-токен не включать одновременно в два конкурирующих polling-процесса.

### 4. Переключение

После согласования остановить старый gateway и его дублирующие расписания; выполнить финальную синхронизацию состояния; запустить новый gateway как service. С исходного Mac не удалять данные и не отзывать доступы до окончания проверки.

В Linux установка system service доступна локальной CLI с параметрами `--system` и `--run-as-user`; фактическую команду и нужные права нужно проверить уже на целевой машине.[2] Не использовать root как повседневного исполнителя агентских инструментов.

### 5. Приёмка и откат

Проверить Telegram из существующей группы и лички, сохранение темы/истории, запуск после перезагрузки хоста, расписания, доставку уведомления, отсутствие двойных ответов, доступы к проектам. Зафиксировать фактические результаты, а не только status сервиса.

Если приёмка не проходит: остановить новый экземпляр, исключить конкуренцию, вернуть старый gateway. Изменения после точки экспорта учитывать отдельно; не обещать откат без потери новых записей, если не предусмотрена их обратная синхронизация.

## Telegram ID

`User.id` обозначает пользователя, `Chat.id` — чат. Это разные идентификаторы; имя и @username не заменяют числовой ID.[3] ID владельца уже есть в локальной карте: `7098788894`. ID новой учебной группы и ученика ещё не получены.

Предлагаемый безопасный способ получения: ученик пишет боту в личку, в новую группу добавляют бота и отправляют адресованное ему сообщение; затем берём ID из полученного события/сохранённого контекста. Не запускать второй getUpdates-потребитель поверх рабочего gateway ради поиска ID. Сам факт сообщения не выдаёт ученику доступ: разрешение владельца оформляется отдельно.
