# Проверки на живой системе

Список классов (`anti-patterns/security.md`) проверяется чтением кода. Этот
файл — про то, чего чтением кода не видно: состояние боевого сервера,
поведение под нагрузкой, реально применённые политики.

Ключевая мысль: **конфиг показывает намерение, сервер показывает факт.**
Расхождение между ними — само по себе находка, и находят его только так.

Универсален: методика одна для любого стека, конкретные команды и адреса
берутся из `docs/projects/<проект>/security-profile.md`.

---

## Слой 1. Снаружи — глазами злоумышленника

Что видно любому, у кого есть адрес сайта. Самое дешёвое и самое полезное:
проверяет ровно то, с чего начинает атакующий.

Инструмент — `.claude/scripts/security-external-check.sh <домен>`.

Что проверяет:

| Проверка | Почему важно |
|---|---|
| Заголовки безопасности | Отдаются ли на самом деле, а не «в коде написано» |
| Служебные пути (`/.git/`, файл окружения, дампы, архивы) | Через это сливают весь исходник и все секреты разом |
| Листинг директорий | Раскрывает структуру и забытые файлы |
| Версии сервера и фреймворка в заголовках | Подсказка, какой эксплойт пробовать |
| Сертификат: срок и протокол | Протухший сертификат = недоступность |
| Перенаправление с HTTP на HTTPS | Иначе сессию можно перехватить |
| Ответ на запрос несуществующей страницы | Не сыплет ли стек-трейсом |

Запускать после каждой выкатки. Занимает секунды, денег не стоит.

## Слой 2. Изнутри сервера

Что снаружи не видно, а ломает так же больно. Нужен способ выполнить команду
на сервере — он указан в профиле проекта.

Что смотреть:

- **Какие порты реально слушают** — не что написано в конфиге оркестрации, а
  что открыто на самом деле. База, кэш, хранилище, панели не должны смотреть
  наружу.
- **Политика файлового хранилища по факту** — приватные объекты не отдаются
  публично.
- **Права на каталог загрузок** — исполняется ли там код, если залить не
  картинку.
- **Режим работы** — отладка выключена, боевой режим включён.
- **Резервные копии** — существуют, свежие, лежат не на том же диске.
- **Сертификат и автопродление** — когда истекает.
- **Кто заходил на сервер** — последние входы, неожиданные адреса.

## Слой 3. Активные тесты защиты

Самый ценный слой: он **доказывает**, что защита работает, вместо
предположения по коду. Пишется как обычные тесты и гоняется на каждой
выкатке.

| Тест | Что доказывает |
|---|---|
| Пользователь A запрашивает ресурс пользователя B | Проверка владельца реально работает |
| Сто запросов подряд на вход или на код | Ограничение частоты срабатывает |
| Пятьдесят одновременных применений купона | Нет состояния гонки: применился один раз |
| Запрос на обновление с полем роли в теле | Массовое присвоение не проходит |
| Вебхук без подписи и с чужой подписью | Отклоняется до записи в базу |
| Заказ с ценой, присланной клиентом | Сервер пересчитал сам |
| Повторная доставка того же вебхука | Обработан один раз |

Сценарии универсальны, реализация зависит от стека. Писать их надо один раз —
дальше работают сами.

**Владелец слоя — `qa-engineer`.** Это обычные тесты, просто проверяют они не
функциональность, а защиту. Агенты `security-*` находят, что проверить;
пишет и поддерживает — `qa-engineer`.

Это единственный слой, который превращает «в коде проверка есть» в
«проверено, и проверяется постоянно».

## Слой 4. Сканер по живому сайту

Автоматический обход сайта с попытками типовых атак. Ловит то, что не
догадались протестировать вручную.

Оговорка: даёт много ложных срабатываний, первый прогон требует отсеивания
шума. Запускать по расписанию, не на каждой выкатке.

## Слой 5. Человек

Пентест перед крупным запуском или раз в год. Единственный слой, который
найдёт логическую дыру, о которой никто не подумал: машина ищет известные
классы, человек ищет **вашу конкретную бизнес-логику**.

---

## Чего не закроет ни один слой

- Компрометация аккаунтов разработки и выкатки — репозиторий, хостинг, почта.
  Обходит всё разом. Защита одна: двухфакторная проверка везде.
- Уязвимость, о которой ещё никто не знает.
- Социальная инженерия.
- Доступы, оставшиеся у ушедших подрядчиков.

Первый пункт — самый вероятный. Двухфакторная защита на рабочих аккаунтах
даёт больше безопасности, чем половина этого документа.

## Как мерить результат

Не процентами. Тремя вопросами:

1. **Сколько классов атак закрыто** — слои 1–4 закрывают почти всё, что
   реально эксплуатируют у проектов такого размера.
2. **Как быстро заметим** — упирается в наблюдаемость.
3. **Как быстро восстановимся** — упирается в проверенные бэкапы.

Отсутствие находок никогда не равно отсутствию уязвимостей.
